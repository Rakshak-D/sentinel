## G. Deviations and unresolved ambiguities

- The Master Blueprint presents uv as a candidate tool for installation/locking, with its exact pin unverified. CR0-A uses the owner's requested pyenv + pip workflow and records the deviation from the table's `SQLite/uv tools` alternative for F46 in ADR-0001. Locking/offline requirements remain CR0 exit gates.
- The blueprint assigns capability dependencies and release exits but does not give a one-to-one release label for every F01-F46 row. The feature release column is a dependency-based planning map, not a quoted blueprint assignment.
- The blueprint requests the broader CR0 skeleton. CR0-A implements only package governance and two real CLI commands; remaining CR0 work is intentionally incomplete.
- CR0-C interprets the first migration as the minimum legitimate slice: it creates only `schema_migrations` and its required `applied_at` index. The broader §10 application schema is deliberately not synthesized in this slice.
- CR0-C correction root cause: the first storage implementation compared every database to a single foundation-only `EXPECTED_SCHEMA_OBJECTS` set after every migration, so a trusted migration adding application tables or indexes was rolled back. The correction selects a complete trusted schema checkpoint from the validated applied migration prefix; it does not learn allowed objects from SQLite contents.
- CR0-D correction root cause: `ModelRequest` and `ModelAdapterRegistration` allowed slash-containing provider model IDs, while `ModelInvocation` and `ModelResponse.provider_model_id` used the narrower `GatewayIdentifier`. The correction uses the existing `ModelIdentifier` type alias for every provider model-ID field and validates registration values through that same Pydantic type definition.
- CR0-E event-schema interpretation: the blueprint requires sanitized small metadata and redaction of Authorization, cookies, email bodies, and access-token data but does not define a diagnostic DTO. This slice uses a fixed event-code/severity/outcome vocabulary, UTC timestamp, optional UUID correlations, a fixed component enum, optional existing sensitivity enum, and optional registered error code. It has no free-form message or metadata map. No material blueprint deviation was required.
- CR0-F configuration interpretation: §12's bundled layer is represented by the `sentinel.config.v1` subset documented below. User/profile/project/CLI layers and activation remain unsupported; unknown fields fail validation. The only timezone accepted in this slice is `UTC` because the Windows project environment has no IANA timezone database and no dependency change is in scope; non-UTC timezones remain unsupported. The external-write switch names correspond to the four existing email/GitHub write capabilities. This narrows the future schema surface but does not enable a capability or authorize a configuration; it is recorded as an ordinary bounded-slice interpretation, not a material architecture deviation.
- CR0-G credential interpretation: `SecretRef` matches the normative §10 `secret_refs` field names; this slice accepts bounded namespaced keychain aliases (`sentinel:<alias>`) as opaque locators and stores no value in the reference. Production broker construction exposes status only and reports unavailable/unknown because no authenticated internal operation principal or verified OS keychain worker exists. Synthetic storage/retrieval is explicitly test-only and process-memory-only. No keyring package or production backend was added; this conservative boundary is not a material blueprint deviation.
- CR0-J demo interpretation: a single fixed `sentinel.demo-fixture.v1` UTF-8 package resource has pinned SHA-256 `365c9f02f1375c3e784138b7cdb3c2fd3ed1a0f4cf64cfec6fdef2fe5d9ecbb8`. Its strict frozen Pydantic schema contains a fictional PUBLIC source note, a deterministic model-output prefix and expected output, and one read-only lookup key/value; it cannot specify adapters or execution destinations. `sentinel demo` calls the current gateway methods through trusted application-registered in-memory adapters, verifies request/response digests and fixed denial probes, and emits sorted compact `sentinel.demo.v1` JSON without bodies, timestamps, random IDs, credentials, or filesystem paths. Only the public fixture bytes are registered for model payload resolution; synthetic SECRET/PRIVATE probes pass references and labels to the gateway but no raw sensitive canary is put in its payload registry. The config hash is reported as an identifier only, never as authorization. This is a §16 fixture/demo deliverable, not a policy test or production model/tool security proof; no ADR was required.
- CR0-K pinning interpretation: `requirements/cr0-windows-py311.lock` is a complete exact-version, per-wheel SHA-256 pip install lock for the runtime closure on Windows x64 / CPython 3.11.7. The wheelhouse is staged externally and is not committed. The lock uses the live-resolved Pydantic 2.14.2 and Typer 0.27.3, which satisfy Sentinel's metadata constraints; it does not pin dev/build tools or establish another OS/Python target. Two builds with `SOURCE_DATE_EPOCH=1793687886`, `build==1.6.1`, and isolated `setuptools==84.2.1` produced identical wheel bytes in this environment; this is same-environment evidence only, not a claim of cross-toolchain or cross-platform source-build reproducibility. - CR1-A normalization interpretation and API: `sentinel.normalization` exports `PlainTextSourceDescriptor`, `NormalizedPlainTextSource`, `NormalizationError`, `NormalizationErrorCode`, `normalize_plain_text(descriptor, raw_content, mime_type)`, `add_citation(source, *, span_id, start_byte, end_byte, expected_text=None)`, and `verify_citation(source, citation, *, original_bytes=None, expected_text=None)`. The caller supplies an immutable descriptor; asserted trust and sensitivity are copied exactly and are not authenticated by normalization. The supported MIME grammar is `text/plain` or one `charset=utf-8` parameter, case-insensitive with optional surrounding ASCII spaces/tabs; duplicate parameters, unknown parameters, unsupported charsets, malformed MIME, and other media types fail closed. UTF-8 decoding is strict and limited to 1,048,576 original bytes. The implementation preserves BOMs, control characters, line-ending bytes, Unicode canonical form, and all original bytes; it performs no normalization that would invalidate byte coordinates. Citations use explicit half-open UTF-8 byte offsets and recheck the full source digest, envelope membership, byte boundaries, and slice digest. This is a conservative §10 source-item/source-span foundation, not an external-source authentication boundary or full F12. No material blueprint deviation or ADR was required.
- CR1-A1 citation-provenance correction: `SourceBoundCitation` is immutable, strict, and `extra="forbid"`; it combines `source_id`, the existing `Sha256Digest` `content_sha256`, and the existing `ByteSpan`. `bind_citation(source, citation)` revalidates the normalized source and span, confirms span membership, and checks source/slice hashes. `verify_bound_citation(source, bound_citation, *, original_bytes=None, expected_text=None)` revalidates both values, matches source UUID and full digest, verifies actual source bytes, membership, UTF-8 boundaries, exact slice digest and optional text, then returns the cited text. The existing `verify_citation` remains source-local: it confirms membership and byte integrity for the supplied source, but a standalone `ByteSpan` does not retain its originating source identity. Future cross-source and persisted consumers must use the bound type. Neither API authenticates a provider or proves the caller's source ID/trust assertion. The reproduced pre-correction case used source IDs `08a35075-fc8f-4d7a-9825-b06c3704e9cb` and `6481174b-84cc-4f17-b57f-629822f857a4`, identical bytes `b"alpha"`, and reused span UUID `f5ae0ef3-f695-47d8-9a94-33d109286628`, range `[0,5)`: spans compared equal and `verify_citation(source_b, source_a_span)` returned `"alpha"`. No schema, dependency, gateway, database, migration, or CR0 artifact changed; no ADR was required.
- CR1-B fixture-reader interpretation: only `read_packaged_github_fixture()` is public; fixture parsing uses the fixed package resource and a pinned SHA-256, strict UTF-8/JSON, duplicate-key rejection, frozen strict Pydantic models, bounded byte/record counts and fixed non-sensitive errors. - CR1-D writer-ownership interpretation: `sentinel.storage.acquire_writer_lease(database)` uses a Windows `Global\` named mutex keyed by a SHA-256 of the selected file's available volume/file ID, falling back to the canonical path only when a file ID is unavailable. It fail-fast waits 0 ms, while each SQLite `BEGIN IMMEDIATE` uses a 500 ms busy timeout. The selected path must be absolute, existing, regular, and on a fixed, removable, or RAM disk; UNC, mapped remote, unknown/no-root, and optical drive types are rejected before database resolution. Existing trusted migration IDs/order/digests, schema checkpoint, SQLite integrity, and foreign-key integrity are validated with existing migration machinery before ownership is returned; the connection then enables foreign keys, requires existing WAL mode, and does not apply migrations or change journal mode. Successful scopes explicitly commit; errors roll back; process termination releases the OS mutex and SQLite rolls back an uncommitted transaction. The lease is thread-bound. This coordinates cooperating callers only; it does not authenticate a Windows user or stop noncooperating processes from writing SQLite directly. The default mutex ACL is token-derived; cross-user access is not promised. UNC, mapped remote, unknown/no-root, and optical paths are tested as refused before database access.

## G. Deviations and unresolved ambiguities

- The Master Blueprint presents uv as a candidate tool for installation/locking, with its exact pin unverified. CR0-A uses the owner's requested pyenv + pip workflow and records the deviation from the table's `SQLite/uv tools` alternative for F46 in ADR-0001. Locking/offline requirements remain CR0 exit gates.
- The blueprint assigns capability dependencies and release exits but does not give a one-to-one release label for every F01-F46 row. The feature release column is a dependency-based planning map, not a quoted blueprint assignment.
- The blueprint requests the broader CR0 skeleton. CR0-A implements only package governance and two real CLI commands; remaining CR0 work is intentionally incomplete.
- CR0-C interprets the first migration as the minimum legitimate slice: it creates only `schema_migrations` and its required `applied_at` index. The broader §10 application schema is deliberately not synthesized in this slice.
- CR0-C correction root cause: the first storage implementation compared every database to a single foundation-only `EXPECTED_SCHEMA_OBJECTS` set after every migration, so a trusted migration adding application tables or indexes was rolled back. The correction selects a complete trusted schema checkpoint from the validated applied migration prefix; it does not learn allowed objects from SQLite contents.
- CR0-D correction root cause: `ModelRequest` and `ModelAdapterRegistration` allowed slash-containing provider model IDs, while `ModelInvocation` and `ModelResponse.provider_model_id` used the narrower `GatewayIdentifier`. The correction uses the existing `ModelIdentifier` type alias for every provider model-ID field and validates registration values through that same Pydantic type definition.
- CR0-E event-schema interpretation: the blueprint requires sanitized small metadata and redaction of Authorization, cookies, email bodies, and access-token data but does not define a diagnostic DTO. This slice uses a fixed event-code/severity/outcome vocabulary, UTC timestamp, optional UUID correlations, a fixed component enum, optional existing sensitivity enum, and optional registered error code. It has no free-form message or metadata map. No material blueprint deviation was required.
- CR0-F configuration interpretation: §12's bundled layer is represented by the `sentinel.config.v1` subset documented below. User/profile/project/CLI layers and activation remain unsupported; unknown fields fail validation. The only timezone accepted in this slice is `UTC` because the Windows project environment has no IANA timezone database and no dependency change is in scope; non-UTC timezones remain unsupported. The external-write switch names correspond to the four existing email/GitHub write capabilities. This narrows the future schema surface but does not enable a capability or authorize a configuration; it is recorded as an ordinary bounded-slice interpretation, not a material architecture deviation.
- CR0-G credential interpretation: `SecretRef` matches the normative §10 `secret_refs` field names; this slice accepts bounded namespaced keychain aliases (`sentinel:<alias>`) as opaque locators and stores no value in the reference. Production broker construction exposes status only and reports unavailable/unknown because no authenticated internal operation principal or verified OS keychain worker exists. Synthetic storage/retrieval is explicitly test-only and process-memory-only. No keyring package or production backend was added; this conservative boundary is not a material blueprint deviation.
- CR0-J demo interpretation: a single fixed `sentinel.demo-fixture.v1` UTF-8 package resource has pinned SHA-256 `365c9f02f1375c3e784138b7cdb3c2fd3ed1a0f4cf64cfec6fdef2fe5d9ecbb8`. Its strict frozen Pydantic schema contains a fictional PUBLIC source note, a deterministic model-output prefix and expected output, and one read-only lookup key/value; it cannot specify adapters or execution destinations. `sentinel demo` calls the current gateway methods through trusted application-registered in-memory adapters, verifies request/response digests and fixed denial probes, and emits sorted compact `sentinel.demo.v1` JSON without bodies, timestamps, random IDs, credentials, or filesystem paths. Only the public fixture bytes are registered for model payload resolution; synthetic SECRET/PRIVATE probes pass references and labels to the gateway but no raw sensitive canary is put in its payload registry. The config hash is reported as an identifier only, never as authorization. This is a §16 fixture/demo deliverable, not a policy test or production model/tool security proof; no ADR was required.
- CR0-K pinning interpretation: `requirements/cr0-windows-py311.lock` is a complete exact-version, per-wheel SHA-256 pip install lock for the runtime closure on Windows x64 / CPython 3.11.7. The wheelhouse is staged externally and is not committed. The lock uses the live-resolved Pydantic 2.14.2 and Typer 0.27.3, which satisfy Sentinel's metadata constraints; it does not pin dev/build tools or establish another OS/Python target. Two builds with `SOURCE_DATE_EPOCH=1793687886`, `build==1.6.1`, and isolated `setuptools==84.2.1` produced identical wheel bytes in this environment; this is same-environment evidence only, not a claim of cross-toolchain or cross-platform source-build reproducibility. This continues the pyenv/pip choice in ADR-0001 and does not require a new ADR.

## H. Open issues and verification blockers

- CR0-K's hash-pinned runtime lock and clean offline install passed only for Windows x64 / CPython 3.11.7. The dev extra and build isolation are not hash-locked. `--no-index` and a local-only wheelhouse disabled pip index access; OS-level network isolation was not tested or applied, so the harness does not sandbox arbitrary package code. The technical lead accepted the recorded evidence but did not independently execute the installation or rehash the wheel. Same-environment timestamp-normalized wheel builds matched, but cross-toolchain source-build reproducibility and other platform support are not claimed.
- The technical lead accepted CR0 §16 for Sentinel 0.1.0 on Windows x64 / CPython 3.11.7, based on independent GitHub source/manifest review and recorded Windows evidence for reviewed SHA `802a18193d740b02b57b179b2683b8a2f3caea9e`. CR0 is `VERIFIED` for that bounded scope only; this is not a production security certification or cross-platform validation. The Windows final-component symlink test remains skipped/unverified. The required CR0-G keychain abstraction is present with its production backend unavailable by design; production OS credential isolation belongs to the later F23/CR7 gate. Full §10 application tables, backup/restore, and configuration layering/activation are not CR0 exit criteria in §16. CR0-J adds the versioned packaged fixture and synthetic demo; doctor remains read-only and does not imply production readiness. CR0-E's diagnostic API is not automatically wired into unrelated operations or third-party logs. CR0-H initializes only a new explicitly selected database.
- CR0-F supplies a strict bundled configuration model only. User/profile/project/CLI layering, complete §12 configuration coverage, persistence, owner-admin provenance, activation state machine, quick evaluation, and binding the effective config hash to authorized gateway execution remain open.
- Decide whether to support any additional Python patch, architecture, or OS; only Windows x64 / CPython 3.11.7 is verified by CR0-K.
- Later policy, authenticated provenance authority, approval, credential isolation, live model/tool adapters, application-wide SQLite writer lease, and external-write gates are entirely unimplemented. Keep external writes disabled.
- CR0-G adds only strict secret-reference metadata, safe availability/existence status, a default unavailable backend, and an explicitly constructed synthetic in-memory test backend. No OS keychain access, owner authentication, isolated credential worker, production value retrieval, signing-key generation, model/tool secret access, or P17 enforcement exists.

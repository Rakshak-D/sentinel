## Chosen scope and architecture

### Scope selection

**INFERENCE:** The strongest 80–120-hour scope is:

1. **Thin personal-agent core:** email ingestion/triage, GitHub monitoring, job collection, local tasks and daily briefing.
2. **Deep feature A — Security Regression Control Plane:** deterministic pre-action authorization plus replayable attack/benign/fault fixtures, approval queues and trace-diff regression.
3. **Deep feature B — Privacy-Aware Static Model Selector:** rule-based selection among Ollama, Gemini, OpenAI and OpenRouter based on task class, sensitivity, latency/cost budget and measured quality.

**INFERENCE:** I would **cut** a learned router, advanced long-term memory, cryptographic audit chaining and broad remote-write automation. The learned router lacks a convincing benefit at your likely data scale; memory is a separate research problem; cryptographic log chaining duplicates current projects such as AgentLock/Agent_Sudo; and broad write capability increases the security/evaluation surface without helping the core thesis. citeturn791140academia7turn724356search4turn174677search6turn174677search7

### Model layer

**FACT:** Current routing literature does not justify building a learned router before establishing a strong static baseline; LLMRouterBench specifically reports that multiple newer approaches fail to reliably beat simple baselines. citeturn791140academia7

**INFERENCE:** Use one provider interface:

`generate(request) -> StructuredResponse`

with adapters for `OllamaAdapter`, `GeminiAdapter`, `OpenAIAdapter`, and `OpenRouterAdapter`.

**INFERENCE:** Configuration should specify per model: `provider`, `model_id`, `local`, `supports_structured_output`, `supports_tools`, `max_context`, `price_input`, `price_output`, `privacy_class`, `timeout_ms`.

**INFERENCE:** Routing order should be deterministic:

1. If `sensitivity >= PRIVATE_RAW`, route local unless a specific policy explicitly permits redacted cloud use.
2. If task has a known local-quality pass rate above the configured threshold, use local.
3. Otherwise select the cheapest measured cloud model meeting the quality and latency threshold.
4. Never allow the model itself to override privacy classification.

**INFERENCE:** The experiment is not “can I invent a smarter router?” It is “how much cloud exposure and cost can a deterministic privacy policy remove at an acceptable measured quality/latency loss?” That is easier to defend technically and aligns with evidence that routing must account for quality, cost and latency while privacy introduces another orthogonal constraint. citeturn791140search3turn791140search5turn791140academia8

### Evaluation design

**FACT:** Security evaluation must measure both unsafe-action suppression and clean-task utility because contemporary benchmarks show that trivial blocking can look secure while destroying usefulness. AgentDyn and WASP make that tradeoff explicit. citeturn173458academia11turn975895academia9

**INFERENCE:** Build **120 fixtures**:

| Category | Type | Cases |
|---|---|---:|
| Benign email/GitHub/job workflows | INFERENCE | 30 |
| Indirect prompt injection | INFERENCE | 30 |
| Provenance/parameter-confusion cases | INFERENCE | 15 |
| Approval/policy edge cases | INFERENCE | 15 |
| Tool failures/timeouts/malformed responses | INFERENCE | 15 |
| Idempotency/retry/partial-failure cases | INFERENCE | 15 |

**INFERENCE:** Keep **80 development cases / 40 sealed test cases**. Do not inspect test attack wording while changing prompts/policies.

**INFERENCE:** For stochastic model components, run each relevant case at least **5 times**; report the mean and a bootstrap 95% confidence interval for unsafe-action rate, clean task success, routing quality and latency. Deterministic policy checks need only one run per fixture unless model output feeds their inputs.

**INFERENCE:** Required security metrics:

### Anti-slop rules

**INFERENCE:** For this project, “AI slop UI” means a surface dominated by generic visual conventions that communicate little system state: gradient hero backgrounds, glowing purple/blue cards, glass panels, oversized chat bubbles, decorative “AI” icons, unexplained KPI cards, excessive rounded containers, emoji substituting for functional icons, and cloned component-library defaults.

**INFERENCE:** Rules:

- No hero section; application opens directly into operational state.
- No gradient backgrounds or decorative glow.
- No chat bubble as the dominant information container.
- Every card/panel must correspond to a real entity: run, approval, policy decision, eval case or source.
- Use border, spacing and typography hierarchy before shadows.
- Use color primarily for state: success, warning, denial/error, selected/focus.
- One icon family only.
- Every chart must answer a comparison question; no “total runs” vanity card without diagnostic purpose.
- Tables default compact.
- Keyboard navigation must cover the approval inbox, trace list and command palette.
- Raw JSON is always accessible from structured views.
- Library primitives are restyled through project-owned tokens rather than shipping recognizable defaults.

### Design brief

**INFERENCE:** Use four primary screens.

**INFERENCE — Control Inbox:** left navigation; center dense list of pending approvals, failed runs and high-priority triage items; right inspection pane showing action, arguments, policy reason, provenance chain and Approve/Reject. Default keyboard sequence: `j/k` select, `Enter` inspect, `a` approve, `r` reject only when focus is not in an input.

**INFERENCE — Run Explorer:** top filter bar; left run list; center LangGraph node timeline; lower/side detail pane for selected node showing prompt version, model route, structured input/output, MCP call and duration. Provide “Create regression fixture” directly from a failed event.

**INFERENCE — Policy/Provenance View:** compact graph showing user intent, source items, derived proposals and tool action; selecting an edge explains which data contributed to an argument. A textual decision explanation is mandatory; the graph is secondary, because graphs become unreadable faster than tables.

**INFERENCE — Eval Lab:** experiment selector, baseline comparison table, metric distributions, failed-case list and case-level replay. Default comparison should be “current commit vs baseline,” not aggregate totals.

**INFERENCE:** Information hierarchy: **decision requiring action → reason → evidence/provenance → raw trace**. Do not make the user inspect a graph before seeing a plain-language decision reason.

**INFERENCE:** Type scale: 12 px metadata, 14 px table/body, 16 px emphasized body, 20 px section title, 28 px page title. Use Inter for UI and JetBrains Mono for IDs, hashes, JSON and trace metadata.

**INFERENCE:** Spacing scale: 4, 8, 12, 16, 24, 32 px. Dense tables use 32–36 px rows; detail panels can use 40–44 px control heights.

**INFERENCE:** Color system should be token-based and restrained. In light mode use neutral near-white surfaces, dark neutral text, a single muted accent for selection/focus, amber for approval/warning, red for denial/error and green only for successful completion. In dark mode invert neutral luminance while preserving semantic hue roles. Verify every text/background pair with automated WCAG contrast checks in CI rather than relying on hand-picked hex values.

**INFERENCE:** Motion: 120–180 ms for disclosure/panel transitions, none for trace timeline updates except small opacity changes, and honor `prefers-reduced-motion`.

**INFERENCE:** Loading state: skeleton only where layout is known; otherwise explicit “loading trace” text with cancellation for long operations. Empty states state *why* the collection is empty and the next relevant action. Error states show error code, retry action and raw details. Never replace actionable errors with “Something went wrong.”
